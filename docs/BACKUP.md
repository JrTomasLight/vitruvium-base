# Резервные копии

Как не потерять систему, если ветку случайно перезапишут или удалят, сломается компьютер или что-то пойдёт не так при крупном изменении.

Защита работает в три слоя: правила веток на GitHub не дают всё сломать, автоматические копии на GitHub хранят снимки за последние 90 дней, локальные копии лежат у вас на диске.

## 1. Правила веток на GitHub (один раз, вручную)

Самая полезная защита: GitHub просто не даст перезаписать историю или удалить ветку.

1. Откройте репозиторий → **Settings → Rules → Rulesets → New ruleset → New branch ruleset**.
2. Название: «Защита веток». **Enforcement status:** Active.
3. **Target branches → Add target → Include by pattern:** `main`, затем ещё раз `features`.
4. Отметьте:
   - **Restrict deletions** — ветку нельзя удалить;
   - **Block force pushes** — историю нельзя перезаписать.
5. Для `main` можно сделать отдельный набор правил и добавить в нём **Require a pull request before merging** и **Require status checks to pass** → `test`. Тогда в `main` попадёт только PR с зелёными тестами. На `features` эти два правила не ставьте: облачные сессии пушат в неё напрямую.
6. **Create.**

Так же можно защитить теги: **New tag ruleset**, шаблон `backup/**` и `v*`, отметки **Restrict deletions** и **Block force pushes**.

## 2. Автоматические копии на GitHub

Workflow **Backup** (`.github/workflows/backup.yml`) собирает все ветки и теги в один файл и хранит его 90 дней. Он запускается:

- при каждом пуше в `main` и `features`, так что у каждого состояния есть копия за последние 90 дней;
- при пуше тега `backup/...`;
- каждый понедельник и вручную (**Actions → Backup → Run workflow**). Эти два способа GitHub разрешает только для workflow из ветки по умолчанию, то есть заработают после слияния `features` в `main`.

Где взять копию: **Actions → Backup →** нужный запуск → внизу страницы раздел **Artifacts**. Там же, на странице запуска, таблица: какие ветки и коммиты попали в копию.

## 3. Перед крупным изменением

Крупное изменение — это:

- слияние `features` в `main`;
- релиз;
- новая версия правил (docx);
- переделка модели данных персонажа: старые миры могут потребовать миграции;
- массовые переименования и перенос файлов.

Перед ним делаем точку восстановления. Копия на GitHub к этому моменту уже есть: она создаётся при каждом пуше. Тег и локальную копию делаете вы на своём ПК. Облачные сессии Claude теги пушить не могут: среда разрешает им только ветки. Claude в облаке напомнит об этом, а Claude на вашем ПК может поставить тег сам.

1. **Тег.** Он отмечает точку в истории и запускает копию на GitHub:
   ```bash
   git tag backup/2026-11-06-pered-main
   ```
   ```bash
   git push origin backup/2026-11-06-pered-main
   ```
   Теги `backup/...` не создают релиз: релиз собирается только по тегам `v...`.
2. **Локальная копия.** Её делаете вы на своём ПК, лучше в папку на облачном диске (Яндекс Диск, Google Drive, OneDrive):
   ```bash
   npm run backup -- "D:\Яндекс Диск\Бэкапы\Витрувий"
   ```
   Без пути копия ляжет в папку `vitruvium-backups` рядом с проектом. Сначала закоммитьте изменения: незакоммиченное в копию не попадает.
3. **Мир Foundry.** Если изменение затрагивает данные персонажей, скопируйте папку мира (`Data/worlds/<мир>`) или сделайте резервную копию встроенными средствами Foundry: на экране настройки, в меню мира.

## Как восстановить

Файл копии (`.bundle`) — это обычный git-репозиторий одним файлом.

**Посмотреть, что внутри:**
```bash
git bundle list-heads vitruvium-backup-2026-11-06-0410.bundle
```

**Развернуть копию в отдельную папку:**
```bash
git clone vitruvium-backup-2026-11-06-0410.bundle vitruvium-restored
```

**Вернуть потерянную ветку на GitHub.** Подключите копию к рабочему проекту и отправьте ветку обратно под новым именем, чтобы сначала сравнить:
```bash
git fetch vitruvium-backup-2026-11-06-0410.bundle "refs/heads/features:refs/heads/restored-features"
```
```bash
git push origin restored-features
```
Дальше откройте PR из `restored-features` или попросите Claude разобраться.

**Вернуться к тегу:**
```bash
git switch -c restored backup/2026-11-06-pered-main
```

## Что в копии нет

Issues, обсуждения, PR и настройки репозитория хранятся на GitHub отдельно от git и в копию не попадают. Важные решения поэтому записываем в репозиторий: в `ROADMAP.md`, `CLAUDE.md` и `CHANGELOG.md`.
