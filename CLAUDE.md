# Витрувий для Foundry VTT

Игровая система для виртуального стола **Foundry VTT** на основе правил настольной ролевой игры **«Витрувий»**.

## Источник правил

- Единственный источник правил: `docs/Vitruvium Beta 3.1.docx`.
- Старые версии (Beta 0.1, Beta 2.0) лежат локально в `ignored-docs/` (папка в `.gitignore`). **Правила из них не используем.** Заимствовать что-то из 2.0 можно только по прямому указанию владельца репозитория.
- Если в правилах не хватает механики или в них есть противоречие, не придумывай решение молча. Спроси владельца или заведи issue.

## Целевая платформа

- **Foundry VTT v13, Build 351.** Поддерживаем только эту версию.
- Обратную совместимость с v12 не делаем. Возможности v14 не используем.
- В `system.json` указываем `compatibility.minimum` и `compatibility.verified` = 13 (verified: `13.351`), `maximum` = 13.
- Используем современные API v13: `TypeDataModel` для данных, ApplicationV2 / `HandlebarsApplicationMixin` для листов. Устаревшие API v12 не используем.

## Структура системы

- id системы: `vitruvium`. Пути в коде: `systems/vitruvium/...`. Папка установки в Foundry обязательно называется `vitruvium`.
- `system.json` — манифест.
- `module/vitruvium.mjs` — точка входа: хук `init` (документы, листы, кубик, `game.vitruvium`) и хуки интерфейса (чат, HUD токена, вкладка «Макросы», панель макросов).
- `module/config.mjs` — справочник правил (`CONFIG.VITRUVIUM`). Числовые константы правил держим только здесь.
- `module/data/` — модели данных (TypeDataModel).
- `module/documents/` — классы документов.
- `module/sheets/` — листы (ApplicationV2).
- `module/dice/` — кубик `dv`, проверка, окно проверки, карточка броска. `rules.mjs` и `probability.mjs` — чистые расчёты без Foundry, их покрывают автотесты.
- `module/actions/` — быстрые действия (`game.vitruvium.actions`): проверка, заявка, бросок кубиков, выдача вдохновения. Их вызывают кнопки листа и HUD, карточки чата и макросы.
- `module/macros/`, `module/apps/macro-library.mjs` — библиотека макросов и её окно. Макрос — одна строка с вызовом действия, логика живёт в системе.
- `module/chat.mjs` — кнопки в карточках чата; `module/hud.mjs` — кнопки на HUD токена.
- `module/helpers/` — общие помощники (склонения и т. п.).
- `module/integrations/` — необязательная поддержка сторонних модулей (Dice So Nice!).
- `module/journals/` — журналы системы в мире Foundry («Изменения системы», «Правила Beta 3.1»): `markdown.mjs` — чистый конвертер Markdown → HTML, `sync.mjs` — создание и обновление журналов при загрузке мира. Компендиумы не используем: база LevelDB в папке системы ломала бы `git pull`.
- `journals/rules.json` — правила для журнала, собранные из docx командой `npm run build:rules` (нужен pandoc). Руками не правим. Изменился docx — пересобираем; автотест сверяет отпечаток.
- `templates/` — Handlebars-шаблоны: `actor/` (лист), `chat/` (карточки), `dialog/` (окна), `apps/` (прочие окна).
- `styles/` — стили, порядок подключения задан в `system.json`: `fonts.css` → `tokens.css` (палитра и шкалы, переменные `--vit-*`) → `components.css` (общие компоненты) → стили отдельных окон. См. «Принципы дизайна».
- `fonts/` — шрифты Alegreya и Alegreya SC (OFL, текст лицензии в `fonts/OFL.txt`). `assets/icons/` — иконки системы (SVG).
- `lang/ru.json` — локализация. В `system.json` она подключена и как `ru`, и как `en`. Так при английском интерфейсе Foundry не показываются сырые ключи.
- `docs/GUIDE.md` — руководство для игроков и мастера. При изменении поведения системы обновляем его.
- `CHANGELOG.md` — журнал изменений для людей, из него же собирается журнал «Изменения системы» в Foundry. Каждое заметное изменение записываем туда в том же коммите, со знаком из легенды: ✅ проверено владельцем в Foundry, 🔧 ждёт проверки, 📄 документы и разработка. Знаки совпадают с ROADMAP: когда пункт плана получает `[x]`, его записи в CHANGELOG получают ✅. Новое — сверху, в разделе «В разработке»; при релизе раздел получает номер версии. Формат проверяет `tests/journals.test.mjs`.
- `docs/BACKUP.md` — резервные копии: правила веток на GitHub, автоматические и локальные копии, восстановление.
- `tests/` — автотесты (Node, `node --test`); `tests/helpers/foundry.mjs` — заглушки Foundry. `package.json`, `scripts/` и `eslint.config.mjs` нужны только для разработки и в релиз не попадают.
- `scripts/package.mjs` — сборка `vitruvium.zip`; список файлов архива — `PACKAGE_FILES` там же. Новую папку системы добавляем туда, иначе её не будет в релизе (`tests/package.test.mjs` это ловит).

## Установка и релизы

- Репозиторий публичный (с 06.11.2026). Пока релизов нет, систему ставят через `git clone ... vitruvium` в `Data/systems` и обновляют через `git pull`. После первого релиза заработает установка по манифесту. Подробности — в README.
- Формы для пользователей: `.github/ISSUE_TEMPLATE/` (ошибка; вопросы и идеи уводятся в обсуждения) и `.github/DISCUSSION_TEMPLATE/` (имя файла = адрес категории обсуждений: `q-a`, `ideas`, `general`, `show-and-tell`). Если владелец переименует категорию и её адрес поменяется, переименовываем файл.
- Релиз собирает `.github/workflows/release.yml` при пуше тега `vX.Y.Z`: версия берётся из тега, к релизу прикладываются `vitruvium.zip` и `system.json`. Теги `v...` и релизы создаём только по указанию владельца.

## Резервные копии

Подробно — в `docs/BACKUP.md`.

- Workflow `.github/workflows/backup.yml` собирает все ветки и теги в git bundle и хранит его артефактом 90 дней: при каждом пуше в `main` и `features`, при пуше тега `backup/...`, а после попадания в `main` ещё еженедельно и вручную.
- **Перед крупным изменением** ставлю тег `backup/ГГГГ-ММ-ДД-<что-дальше>` (латиницей, например `backup/2026-11-06-pered-main`) и пушу его. Это разрешено без отдельного вопроса (указание владельца, 06.11.2026). **Облачная сессия теги пушить не может** (прокси среды отвечает 403): там не ставлю тег, а прошу владельца поставить его с ПК. Копия на GitHub всё равно появится при пуше в `features`. Крупное изменение:
  - слияние `features` в `main`, релиз;
  - новая версия правил (docx);
  - изменение модели данных (`module/data/`), после которого старым мирам может понадобиться миграция;
  - массовые переименования и перенос файлов.
- В ответе владельцу после такого тега напоминаю сделать локальную копию: `npm run backup -- "<папка на облачном диске>"`, а если менялись данные персонажей — копию мира Foundry.
- Правила веток включены (06.11.2026): на `main` и `features` запрещены force push и удаление, исключений нет ни для кого. Меняет их только владелец, см. `docs/BACKUP.md`.

## Принципы дизайна

Главный образ — **тетрадь Леонардо**: система названа по Витрувию, а его «Витрувианский человек» нарисован Леонардо. Всё «бумажное» сделано из материалов мастерской: бумага, железо-галловые чернила, сангина, серебряный карандаш. Значения токенов — в `styles/tokens.css`, общие компоненты — в `styles/components.css`.

### Не копируем официальный сайт

- ⚠️ **Важно.** Оформление системы (листы, окна, карточки в чате, иконки) **не повторяет дизайн официального сайта «Витрувия»**. Не берём оттуда фирменные цвета, шрифты, логотипы, графику и узнаваемую композицию.
- Сейчас официальный сайт недоступен, и сверить с ним текущий дизайн нельзя. Когда сайт заработает, сравниваем оформление и убираем совпадения. Этот пункт записан в `ROADMAP.md` (этап 8).

### Палитра: у каждого пигмента одна роль

| Токен | Пигмент | Hex | Для чего |
|---|---|---|---|
| `--vit-parchment` | бумага | `#f3e9d2` | фон всего «бумажного» |
| `--vit-parchment-deep` | тонированная бумага | `#e6d6b2` | подложки, выделенные зоны (итог броска, панель вкладок) |
| `--vit-ink` | железо-галловые чернила | `#3b2a1a` | основной текст |
| `--vit-ink-soft` | выцветшие чернила | `#6b5640` | подсказки, подписи, контуры кнопок и отметок |
| `--vit-sanguine` | сангина | `#963a21` | значения, активное, главное действие, провал |
| `--vit-sanguine-soft` | растёртая сангина | `#c97b5d` | только заливки (отметки), никогда не текст |
| `--vit-line` | серебряный карандаш | `#b9a37c` | декоративные линии построения, разделители |
| `--vit-terre-verte` | зелёная земля | `#43603a` | **только** успех |
| `--vit-azure` | голубая грунтовка | `#3e5873` | **только** фокус клавиатуры и пометки для мастера |

- В коде пользуемся смысловыми токенами (`--vit-color-accent`, `--vit-color-success`, `--vit-color-failure`, `--vit-color-focus`, `--vit-color-text-muted`), а не пигментами напрямую, если роль совпадает.
- Новые цвета не добавляем «на глаз». Если нужна новая роль, сначала выбираем пигмент из той же мастерской и записываем его в `tokens.css` и в эту таблицу.
- Никаких ярких «экранных» цветов, неона, чисто чёрного `#000` и чисто белого `#fff`. Градиенты — только как фактура бумаги.
- Всё «бумажное» (лист, окна, карточки) всегда светлое, даже в тёмной теме Foundry. Поэтому цвета текста, полей и кнопок внутри заданы явно.

### Шрифты и размеры

- **Alegreya** — весь текст: каллиграфическая гуманистическая антиква с кириллицей, близкая к почерку эпохи. Полужирный (700) — имена и названия, курсив — подсказки и пояснения.
- **Alegreya SC** (500) — подписи полей, вкладки, итоги «Успех» и «Провал». Это настоящие капители. Текст подписей пишем обычным регистром («Сложность»), а не ЗАГЛАВНЫМИ.
- Шкала размеров с шагом 1.2 от размера интерфейса Foundry: `--vit-step--1` (подписи, подсказки) → `--vit-step-0` (текст) → `--vit-step-1` (заголовки карточек) → `--vit-step-2` (значения) → `--vit-step-3` (имя персонажа). Размеры в `rem`, чтобы работала настройка масштаба интерфейса Foundry.
- Отступы кратны `0.25rem` (`--vit-space-1` … `--vit-space-5`).

### Мотивы

- **Круг, вписанный в квадрат** — фирменный знак системы: портрет, грань кубика в чате, иконки макросов. Используем его для того, что относится к персонажу и броску, но не как декор везде.
- **Двойная рамка** (контур и линия рядом) — только у главного элемента: портрет, карточка в чате, главная кнопка экрана.
- **Линии построения** вместо коробок: тонкие линии серебряным карандашом разделяют строки. Без теней, без «карточек в карточках», без одинаково скруглённых плашек. Скругление кнопок и полей почти нулевое (`--vit-radius-control`), круглыми бывают только отметки и портрет.
- **Отметки-кружки** для уровней (характеристики 1–3, вдохновение 0–6): закрашенный кружок сангиной — набранный уровень.

### Компоненты

- `.vit-button` — кнопка действия: чернильный контур, без заливки, при наведении сангина. `.vit-button.primary` — главное действие экрана (сангина, двойная рамка). На экране не больше одной главной кнопки.
- `.field-label` — подпись поля (Alegreya SC). `.hint` — пояснение курсивом.
- `.pips` / `.pip` — отметки уровня. `.vit-face` — грань кубика с отметками успехов.
- `.vitruvium.chat-card` — карточка в чате: `card-header` (заголовок `card-title`, подписи `card-meta`), тело, `card-result`, `card-note`, `card-actions`.
- Новое окно системы получает классы `vitruvium` и своё имя; бумажная основа, поля и кнопки подтянутся из `components.css`. Стили окна — в отдельном файле `styles/<окно>.css`, подключённом в `system.json`.

### Тексты интерфейса

- Коротко, обычным регистром, без канцелярита. Кнопка говорит, что произойдёт: «Бросить», «Заявить», «На панель». Одно действие называется одинаково везде: кнопка «Заявка» → окно «Заявка» → карточка «Заявка».
- Ошибки и пустые состояния объясняют, что сделать: «Выберите токен своего персонажа…», а не «Ошибка».
- Числа — с правильным склонением (`formatCount`: «1 кубик», «3 кубика», «5 кубиков»).
- Не используем шаблонные приёмы: строки через «·», стрелки «→» в кнопках, нумерацию «01/02/03» для того, что не является последовательностью, надписи ЗАГЛАВНЫМИ над каждым заголовком.

### Доступность

- Контраст текста не меньше 4.5:1 на обоих тонах бумаги, контуров элементов и фокуса — не меньше 3:1. Это проверяет `tests/design.test.mjs`: при изменении палитры тест покажет нарушение.
- У каждого интерактивного элемента виден фокус с клавиатуры (голубая грунтовка). Иконки-кнопки подписаны (`aria-label`, `data-tooltip`).
- Анимация только в ответ на действие и короткая; при `prefers-reduced-motion` её нет (`--vit-transition`).
- Информация не передаётся только цветом: у итога проверки есть слово («Успех»/«Провал»), у граней кубика — отметки и подпись.

### Как проверять дизайн

- После правок стилей смотрим результат: в облачной сессии — `npm run preview` (без Foundry, только наши стили и шаблоны, данные готовит код системы на заглушках), у владельца — в Foundry, в светлой и тёмной теме. Те же скриншоты GitHub прикладывает к каждому запуску проверок.
- Новый лист, окно или карточку добавляем в превью (`scripts/preview.mjs`, функция `collectSamples`), иначе их не будет на скриншотах и в проверке доступности.
- Сначала думаем о роли элемента, потом о цвете. Перед тем как добавить украшение, убедитесь, что оно что-то сообщает, иначе уберите.

## Правовой контекст

Правила Beta 3.1 обнародованы: они находятся в открытом тестировании, и распространять их разрешено. Чёткой лицензии на использование правил пока нет, так сообщил разработчик «Витрувия». Поэтому в пользовательских документах не пишем строгих ограничений, а ставим предупреждение о правах (см. «Язык и оформление»). Если лицензия появится, обнови предупреждение по её тексту.

Видимость репозитория (приватный или публичный), публичные релизы и размещение в каталогах Foundry — решения владельца. Сами их не меняем.

Папка `ignored-docs/` хранится только локально. В ней лежат старые версии правил, шаблон персонажа, «Легенда о Визергуте» и «Чужие материалы». Её содержимое в код и репозиторий не переносим. Особенно это касается `ignored-docs/Чужие материалы/`.

## Ключевая механика (Beta 3.1)

Краткая выжимка. Если она расходится с docx, прав docx.

- **Характеристики** (6 штук, уровень от 1 до 3): Телосложение, Движение, Внимание, Мышление, Влияние, Воля.
- **Проверка характеристики.** Бросается столько кубиков, каков уровень характеристики, плюс уровень домена, если используется способность. В пуле не больше 6 кубиков.
- **Кубики.** Особые d6: 3 пустые грани, 2 грани с одним успехом, 1 грань с двумя успехами.
- **Сложность** от 1 до 6, её назначает мастер.
  - Успехов не меньше сложности: проверка успешна.
  - Успехов меньше: провал.
  - Результат близок к сложности: мастер может засчитать частичный успех.
- **Преимущество и помеха.** Делается дополнительный бросок, засчитывается лучший или худший результат соответственно. Максимум два преимущества или две помехи. Преимущества и помехи взаимно нейтрализуют друг друга.
- **Домены и способности.**
  - У персонажа от 1 до 6 доменов, уровень домена от 1 до 3.
  - Каждый уровень домена открывает 2 способности.
  - Домен можно использовать как самостоятельную способность.
- **Атрибуты** (от 1 до 12): особенности персонажа с названием и описанием.
- **Имущество.**
- **Вдохновение.**
  - Максимум 6, мастер выдаёт его в награду.
  - 1 вдохновение даёт +1 кубик к проверке.
  - Если используется способность, 1 вдохновение даёт столько успехов, каков уровень её домена.
- **Уровень персонажа.** От него зависят бюджеты на создание (очки характеристик и доменов, число атрибутов и предметов):
  - Обычный: 3;
  - Редкий: 6;
  - Выдающийся: 9;
  - Легендарный: 12.
- **Статусы, уровни и аспекты.** Это общий инструмент для отслеживания чего угодно:
  - статус — короткое описание;
  - уровень — числовое значение;
  - аспект — ключевой показатель, у которого есть своя шкала уровней и статусы.

## Открытые вопросы по правилам

- **Что даёт уровень домена.** В разделе «Домены и способности» подряд идут два абзаца, и они расходятся. В одном уровень домена добавляет *кубики* к броску. В другом он добавляет *успехи* за 1 вдохновение. Раздел «Вдохновение» описывает второй вариант. Окончательное решение — за владельцем.
- **Боя, развития персонажа и здоровья в Beta 3.1 нет.** Не добавляй их без указания владельца.

## Тестирование

- Систему вручную тестирует владелец в Foundry VTT и присылает отзывы.
- На ПК владельца папка `D:\Foundry VTT\Data\systems\vitruvium` — ссылка (junction) на рабочую папку проекта `D:\Projects\vitruvium`. Foundry видит ту ветку, которая там сейчас выбрана, обычно `features`. Изменения из облачных сессий попадают туда только после `git pull`.
- После правок в JS нужно перезагрузить мир (F5).
- **Автотесты** логики бросков и вероятностей: `npm test` (нужен только Node 20+, зависимостей нет). В GitHub Actions они запускаются при пуше в `main` и `features` и в PR (`.github/workflows/tests.yml`).
  - `tests/rules.test.mjs`, `tests/probability.test.mjs` — чистые правила и точные вероятности;
  - `tests/die.test.mjs`, `tests/check.test.mjs`, `tests/actor.test.mjs` — кубик, проверка и метод актёра на заглушках Foundry;
  - `tests/statistics.test.mjs` — настоящие броски против теории (генератор с зерном, поэтому тест повторяем);
  - `tests/i18n.test.mjs` — все ключи `VITRUVIUM.*` из кода и шаблонов есть в `ru.json`;
  - `tests/journals.test.mjs` — конвертер Markdown, формат `CHANGELOG.md`, журнал правил собран из текущего docx.
- **При изменении механики бросков** (грани, пул, преимущества, вдохновение, домены) сначала меняем ожидания в тестах, потом код. Новые правила расчёта кладём в `module/dice/rules.mjs` или `probability.mjs`, а не в слой Foundry, чтобы их можно было тестировать.
- **Проверки на GitHub** (`.github/workflows/tests.yml`, на каждый пуш в `main` и `features` и на PR):
  - `test` — `npm test`;
  - `lint` — `npm run lint`: ESLint (`eslint.config.mjs`) и проверка шаблонов (`scripts/lint-templates.mjs`: шаблон разбирается Handlebars, хелперы — из списка Foundry v13);
  - `preview` — `npm run preview`: скриншоты листа, окон и карточек чата и проверка доступности axe-core; падает на нарушениях serious и critical;
  - `package` — архив `vitruvium.zip` прикладывается к запуску, его можно поставить в Foundry вручную;
  - `changelog` — предупреждение, если код системы поменялся, а `CHANGELOG.md` нет.
- Для `lint` и `preview` нужны пакеты: `npm ci` (папка `node_modules/` в `.gitignore`), для превью ещё браузер: `npx playwright install chromium`. В облачной сессии Chromium уже стоит. `npm test` работает без пакетов.
- Dependabot (`.github/dependabot.yml`) раз в неделю открывает PR в `features` с новыми версиями actions и пакетов. Перед слиянием смотрим, что проверки зелёные.
- Перед пушем запускаем `npm test` и, если менялись код, шаблоны или стили, `npm run lint` и `npm run preview`.
- `npm run odds` печатает таблицу шансов успеха (пул × сложность, с преимуществами и помехами); `npm run odds -- --bonus 2` — с добавленными успехами. Полезно для оценки баланса.
- Автотесты не заменяют проверку в Foundry: листы, окна, чат и Dice So Nice! проверяет владелец вручную.
